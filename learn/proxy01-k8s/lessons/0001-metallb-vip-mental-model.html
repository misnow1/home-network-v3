Lesson 0001 · Hybrid edge

What the MetalLB VIP actually is

One idea: the address proxy01 will proxy_pass to is not a node IP — it is a service VIP that MetalLB teaches the LAN via ARP.

Why this matters for your mission

You already point nginx at fixed backends (e.g. kif on VLAN 4). Phase 7 does the same shape — but the backend is a LoadBalancer Service IP on VLAN 9 that belongs to Envoy Gateway, not to k8s-node-1 or k8s-cp01. Until that VIP clicks, Gateway and HTTPRoute feel like magic sitting on top of fog.

Knowledge — cloud LB, bare metal edition

On AWS/GCP/Azure, a Service of type LoadBalancer gets a public or VPC IP from the cloud provider. On bare metal there is no cloud controller — so MetalLB fills that gap.

In layer 2 mode (what this lab uses), MetalLB does not invent a fancy router protocol. One cluster node answers ARP for the VIP: “Who has 192.168.9.200?” → that node’s MAC. From the network’s perspective, that machine simply appears to own an extra IP. (MetalLB L2 concepts)

Important limitation (worth remembering for work too): L2 mode steers all traffic for that VIP to one node first; then kube-proxy / the datapath fans out to pods. It is failover-oriented advertisement, not true multi-node L2 load balancing. (same doc)

Two CRs, two jobs

Per MetalLB configuration:

  • IPAddressPool — which IPs MetalLB is allowed to assign (here 192.168.9.200–.210).
  • L2Advertisement — announce those IPs with ARP/NDP on the LAN.

Envoy Gateway’s Service is type LoadBalancer, pinned to 192.168.9.200 via annotation (runbook Phase 5). MetalLB assigns that EXTERNAL-IP; speakers advertise it. proxy01’s upstream is then just http://192.168.9.200.

Internet │ ▼ proxy01 (TLS + Authelia) ← you already own this │ plain HTTP upstream ▼ 192.168.9.200 ← MetalLB VIP (ARP on VLAN 9) │ lands on one speaker node ▼ Envoy Gateway pods ← next lesson: Gateway / HTTPRoute │ ▼ Service → Pods
Nginx map: think of 192.168.9.200 as a keepalived-style VIP for the Envoy front door — except Kubernetes owns the Service object, and MetalLB owns the ARP. You do not put a worker’s node IP in reverse_proxy_sites.

Skill — prove the VIP is alive (LAN side)

Before changing proxy01, confirm the VIP answers from a host that can reach VLAN 9 (proxy01 itself, or your admin box if routed). From the runbook: 

kubectl get svc -n envoy-gateway-system
# EXTERNAL-IP should be 192.168.9.200

# From proxy01 / VLAN 1 with firewall allowing it:
curl -sS -o /dev/null -w '%{http_code}\n' http://192.168.9.200/
# Want: connection refused or HTTP status — NOT a timeout

Timeout ⇒ routing/firewall/ARP problem (VIP not advertised or VLAN 1→9 blocked). Refused/404 ⇒ packets reached something on that IP — MetalLB path is working; L7 routing may still be incomplete.
