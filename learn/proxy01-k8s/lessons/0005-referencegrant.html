Lesson 0005 · Hybrid edge

ReferenceGrant — when routes and Services diverge

One idea: attaching a route to a Gateway and pointing a route at a Service in another namespace are two different trust handshakes.

Why this matters for your mission

Your whoami path kept the HTTPRoute and Service in the same whoami namespace — so you never needed a ReferenceGrant. Work clusters often split “edge routes” and “app Services” across namespaces. Without the grant, you get Accepted=False / unresolved refs that look like random 502s (lesson 0004).

Knowledge — two handshakes

Per Gateway API security and ReferenceGrant:

Cross-namespace link Who must agree ─────────────────────────────── ───────────────────────────── HTTPRoute → Gateway (attach) Gateway.allowedRoutes (NOT ReferenceGrant) HTTPRoute → Service other NS ReferenceGrant in the *Service’s* namespace (from: HTTPRoute ns)

Your lab Gateway already allows routes from all namespaces (allowedRoutes.namespaces.from: All in the runbook). That only covers attach. Forwarding to a backend in another namespace still needs an explicit grant in that backend namespace.

What a grant looks like

The grant lives next to the target (the Service). from = trusted callers; to = kinds (and optional name) in this same namespace that may be referenced. 

# Lives in namespace "apps" — where the Service is
apiVersion: gateway.networking.k8s.io/v1beta1
kind: ReferenceGrant
metadata:
  name: allow-edge-routes
  namespace: apps
spec:
  from:
    - group: gateway.networking.k8s.io
      kind: HTTPRoute
      namespace: edge          # where the HTTPRoute lives
  to:
    - group: ""              # core API group
      kind: Service
      # name: whoami        # optional; omit = any Service in apps

Matching route fragment (namespace edge): 

backendRefs:
  - name: whoami
    namespace: apps
    port: 80
Security detail: without a grant, implementations must treat the cross-namespace ref as invalid and must not leak whether the remote Service exists. Status focuses on “no ReferenceGrant,” not “Service missing.” (same docs)
Your live whoami does not need this today (route + Service same NS). Learn the shape now so Phase 9 / work clusters do not surprise you.

Skill — spot when you need one

Optional lab drill (safe): create a throwaway route in another namespace that backendRefs the existing whoami Service with namespace: whoami, observe status without a grant, then add the grant in whoami and re-check. Clean up when done. 

kubectl -n <route-ns> describe httproute …
# Look for ResolvedRefs=False / reason about ReferenceGrant

kubectl -n whoami get referencegrant
# After grant: ResolvedRefs=True (assuming Service/port OK)
