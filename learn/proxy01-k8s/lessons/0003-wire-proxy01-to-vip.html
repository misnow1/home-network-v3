Lesson 0003 · Hybrid edge · Phase 7

Wire proxy01 to the MetalLB VIP

One idea: Phase 7 is not new nginx knowledge — it is pointing an existing reverse_proxy_sites entry at 192.168.9.200 and making four names agree.

Why this matters for your mission

Lessons 0001 and 0002 proved the LAN path: VIP → Envoy → HTTPRoute → whoami. Your mission’s done check is the public curl through proxy01 (TLS + Authelia). That is just another upstream — VLAN 9 VIP instead of kif VLAN 4.

Knowledge — what changes vs a Docker backend

You already add sites per reverse-proxy-runbook site schema. Compose apps use proxy_pass: http://192.168.7.152:PORT. Kubernetes apps use the MetalLB VIP on port 80 — Envoy does Host-based routing afterward.

Compose app backend K8s app backend (Phase 7) ───────────────────── ────────────────────────── proxy_pass proxy_pass http://192.168.7.152:PORT http://192.168.9.200 (kif br4, one port/app) (one VIP; many Hosts via HTTPRoute) TLS + Authelia on proxy01 TLS + Authelia on proxy01 ← unchanged

The four-name contract

Traffic fails in confusing ways if these disagree. They must be the same public hostname (example: whoami.2123studios.com):

  1. DNS — A/AAAA (or CNAME) → proxy01’s public address
  2. certbot SAN — name in certbot_domains
  3. nginx — server_names in reverse_proxy_sites
  4. HTTPRoute — spec.hostnames (what Envoy matches)
nginx should forward the client Host (your shared proxy snippet does). Envoy then selects the route. If nginx rewrote Host to the VIP IP, every request would 404 on the Gateway — same failure mode as lesson 0002’s bare-IP curl.

Site shape (matches the role schema)

The runbook Phase 7 snippet is a pattern sketch. Prefer the real schema — auth_required lives on the location, not as a top-level site key (site schema): 

- name: whoami.2123studios.com
  server_names:
    - whoami.2123studios.com
  locations:
    - path: /
      proxy_pass: http://192.168.9.200
      auth_required: true
      rate_limit:
        zone: proxied_apps
        burst: 20

Pair that with an HTTPRoute whose hostnames list includes whoami.2123studios.com (update the Phase 5 whoami route if it still says whoami.home.… only).

Authelia rules on kif must allow the new domain (same as any other Authelia-gated vhost). Edge policy: edge-access-model.md. Production apply uses ./scripts/prod-run.sh --confirm-production -- — never bare ansible-playbook -i inventories/production.

Skill — land Phase 7 end-to-end

Work this checklist when you are ready to touch prod inventory (or lab first):

  1. LAN still green: curl -sS -H 'Host: <name>' http://192.168.9.200/
  2. Add FQDN to DNS + certbot_domains; issue/renew cert
  3. Add reverse_proxy_sites entry → http://192.168.9.200
  4. Align HTTPRoute hostnames with that FQDN
  5. Update Authelia access_control if auth_required: true
  6. ./scripts/prod-run.sh --confirm-production -- playbooks/reverse-proxy.yml --limit proxy01… (and certbot playbook if the SAN is new)
  7. Done check: curl -sS -I https://<name>/ — expect Authelia challenge or app body after login, not 502/timeout
# From an admin host after apply (auth may redirect):
curl -sS -o /dev/null -w '%{http_code}\n' https://whoami.2123studios.com/
# 302/401 toward Authelia = edge alive; 502 = VIP/Gateway/route; timeout = firewall
