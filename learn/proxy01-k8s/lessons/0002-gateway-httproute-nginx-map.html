Lesson 0002 · Hybrid edge

Gateway + HTTPRoute as nginx, in CRDs

One idea: MetalLB delivers packets to Envoy; Gateway / HTTPRoute decide which app gets which Host — the same job as server_name and location.

Why this matters for your mission

Lesson 0001 got traffic to 192.168.9.200. Phase 7 still needs L7 routing: many public names share one VIP, just like many nginx vhosts share one proxy01 IP. Gateway API is how the cluster expresses that — and it is what you will see at work instead of (or beside) classic Ingress.

Knowledge — three kinds, three roles

Per the Kubernetes Gateway API docs, the stable model splits by role:

  • GatewayClass — “which controller implements this?” (here Envoy Gateway). Like choosing the nginx package / ingress controller once for the cluster.
  • Gateway — a listener front door (port, protocol, which routes may attach). Like the shared listen 80 / site-enabled skeleton on the VIP.
  • HTTPRoute — Host + path rules → Service. Like one vhost’s server_name + location + proxy_pass.
nginx mental model Gateway API (this lab) ───────────────────── ──────────────────────────── listen + shared IP → Gateway (listener :80 on VIP) server_name foo.com → HTTPRoute.hostnames location / { ... } → HTTPRoute.rules.matches proxy_pass backend → HTTPRoute.rules.backendRefs (controller choice) → GatewayClass → Envoy Gateway

Your cluster’s concrete objects

From the runbook Phase 5:

  • GatewayClass/eg → controller gateway.envoyproxy.io/gatewayclass-controller
  • Gateway/eg in envoy-gateway-system — HTTP :80, allowedRoutes.namespaces.from: All (app routes may live in other NS)
  • Envoy’s Service is LoadBalancer pinned to the MetalLB VIP

TLS stays on proxy01. The Gateway listener is plain HTTP on purpose — Authelia and certbot never move into this lesson.

HTTPRoute — the bit you will write per app

An HTTPRoute attaches to a Gateway with parentRefs, matches the Host header via hostnames, then forwards to a Service via backendRefs. Request flow from the same docs: client → Gateway address → Host match → optional path match → backend. 

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: whoami
  namespace: whoami
spec:
  parentRefs:
    - name: eg
      namespace: envoy-gateway-system
  hostnames:
    - whoami.home.2123studios.com
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /
      backendRefs:
        - name: whoami
          port: 80
Critical: curling the VIP without a matching Host header yields 404. Envoy is doing vhost routing — same as hitting an IP with the wrong server_name. Always: -H 'Host: whoami.home.2123studios.com'.
Attachment is bidirectional: the route names the Gateway (parentRefs), and the Gateway must allow that route’s namespace (allowedRoutes). If either side refuses, status shows Accepted=False — not a silent nginx misconfig.

Skill — whoami over the VIP (LAN)

If whoami is not already deployed, use the runbook smoke test. Then verify acceptance and Host-based routing: 

kubectl -n whoami get httproute whoami -o wide
kubectl -n whoami describe httproute whoami
# Want: Accepted=True, ResolvedRefs=True

curl -sS -H 'Host: whoami.home.2123studios.com' http://192.168.9.200/
# Want: whoami text body

curl -sS -o /dev/null -w '%{http_code}\n' http://192.168.9.200/
# Want: 404 (no Host match) — proves L7 routing, not “any HTTP works”
